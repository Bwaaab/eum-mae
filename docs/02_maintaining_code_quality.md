# 코드 품질 유지

본 문서는 음메 저장소에 코드를 넣는 규칙과, 품질을 유지하기 위한 수단을 정의한다. 자동 검사의 단계와 한계는 [CI 파이프라인](./01_ci-pipeline.md)을 따른다. 역할과 소통은 [팀 약속](./00_team-agreement.md)을 따른다.

---

## 1. 품질을 유지하는 수단

1. **리뷰**  
   동작뿐 아니라 가독성, 책임 분리, 재현 가능 여부를 확인한다. 작성자는 자신의 PR을 단독 승인하지 않는다. 풀 리퀘스트 리뷰는 48시간 이내를 목표로 한다.

2. **자동화 (CI)**  
   GitHub Actions가 린트와 테스트 등 반복 가능한 검사를 수행한다. 구성은 CI 파이프라인 문서를 따른다.

3. **작은 변경**  
   PR은 한 가지 목적만 담는다. 룰렛, 리스트, 문서, 리팩터를 한 PR에 섞지 않는다.

4. **테스트와 수동 확인**  
   자동 테스트와 실제 실행을 함께 한다. 화면이 바뀌면 PR에 스크린샷과 확인 절차를 남긴다.

5. **규칙 문서화**  
   이슈·PR 템플릿과 커밋 형식을 저장소에 둔다. 빈 이슈와 빈 PR은 받지 않는다.

6. **공통 파일 보호**  
   `main.py`와 공유 코드를 변경할 때는 이슈 댓글로 먼저 알린다. 리뷰·품질 담당은 충돌과 회귀를 중점적으로 본다.

---

## 2. 기여 규칙

기여 규칙은 이 저장소에 코드를 넣는 절차이다. 기여자는 다음 순서를 따른다.

1. 작업 전 이슈를 등록한다
2. `feat/…`, `fix/…`, `refactor/…` 형식의 브랜치를 만든다
3. 커밋 메시지와 PR 제목을 아래 컨벤션에 맞춘다
4. 종류에 맞는 PR 템플릿을 채운 뒤 리뷰를 요청한다
5. CI가 통과하고 리뷰가 승인된 뒤에만 `main`에 병합한다

규칙을 두는 이유는 리뷰 비용을 줄이고, 이력을 검색 가능하게 하며, 깨진 코드가 `main`에 들어가는 일을 막기 위함이다.

### 이슈 템플릿

`config.yml`에서 빈 이슈를 허용하지 않는다. 다음 중 하나를 선택한다.

| 파일 | 제목 접두사 | 용도 |
|---|---|---|
| `bug-report.yml` | `[버그]:` | 오류 보고. 운영체제, 재현 단계, 기대·실제 동작 |
| `feature-template.yml` | `[기능]:` | 기능 제안. 문제 또는 사용 맥락, 제안, 대안 |
| `qua-report.yml` | `[질문]:` | 버그·기능이 아닌 질문 |

버그 이슈의 재현 칸은 버그 수정 PR과, 기능 이슈의 맥락·제안 칸은 기능 PR과 대응한다.

### 풀 리퀘스트 템플릿

빈 PR은 열지 않는다. `config-pr-template`에서 종류를 고른다.

| 파일 | 용도 | 이슈 연결 |
|---|---|---|
| `bug-fixes-pr-template.md` | 버그 수정 | `Fixes #` |
| `feature-pr-template.md` | 기능 추가 | `Closes #` |
| `default-pr-template.md` | 리팩터, 잡무, 문서, CI | 해당 이슈가 있으면 연결 |

공통으로 채울 항목은 요약, 범위(리스트 / 룰렛·카드 / 결과창 / 이펙트 / 공통 / 문서·CI), 테스트 계획, 리뷰어 참고이다.

버그 수정 PR은 원인, 수정 내용, 수정 전 재현과 수정 후 확인, 환경(운영체제, Python, eum-mae 버전)을 적는다. 기능 PR은 문제 또는 사용 맥락, 제안·구현 방법, 대안, 인터페이스 변경, 정상·예외 경로를 적는다.

리뷰 요청 전에 템플릿의 테스트 계획을 채운다. 린트·테스트가 구성되어 있으면 통과시켜 둔다.

## 3. 커밋 컨벤션

커밋 메시지는 다음 형식을 사용한다.

```
타입(범위): 변경 요약
```

| 타입 | 의미 | 예 |
|---|---|---|
| `feat` | 새 기능 | `feat(list): 메뉴 삭제 추가` |
| `fix` | 버그 수정 | `fix(roulette): 빈 목록에서 크래시` |
| `refactor` | 동작은 같고 구조만 정리 | `refactor(result): 상태 분리` |
| `chore` | 도구, 의존성, CI | `chore: lint 설정 추가` |
| `docs` | 문서만 | `docs: 기여 규칙 초안` |
| `test` | 테스트만 | `test(list): 중복 메뉴 케이스` |

범위는 담당 기능과 맞춘다. `list`, `roulette`, `result`, `effects`, 공통은 생략하거나 `common`을 쓴다.

브랜치, 커밋, PR 종류는 서로 대응한다. `fix/…` 브랜치의 커밋은 `fix:`, PR은 버그 수정 템플릿을 사용한다. `feat/…`는 기능 템플릿을 사용한다.

## 4. GitHub Actions

GitHub Actions는 `.github/workflows/*.yml`에 정의한 명령을, PR 또는 push 시점에 원격 실행 환경에서 수행하는 기능이다.

| 용어 | 의미 |
|---|---|
| Workflow | 워크플로 파일 하나. 예: `ci.yml` |
| Event (`on:`) | 실행 시점. `pull_request`, `push` 등 |
| Job | 한 실행 환경에서 수행하는 작업 묶음 |
| Step | job 안의 개별 명령 또는 재사용 Action |
| Action | 재사용 단위. 예: `actions/checkout@v4` |
| Runner | 명령을 실행하는 서버 |

본 프로젝트의 CI는 `ci.yml` 하나를 최소 구성으로 한다. PR이 열리거나 갱신되면 의존성을 설치하고 린트와 테스트(있는 경우)를 실행한다. 상세한 단계와 한계는 CI 파이프라인 문서를 따른다.

Actions 환경에는 기여자 개인의 로컬 파일과 비밀 값이 없다. 이슈·PR 템플릿에서 실행 가능 여부를 확인하는 이유이다.

---

## 5. 리뷰 기준

리뷰·품질 담당은 PR 템플릿이 채워졌는지와 다음을 확인한다.

1. 관련 이슈가 `Fixes #` 또는 `Closes #`로 연결되어 있는가
2. 범위 표시가 실제 변경 파일과 맞는가
3. 버그면 재현과 수정 후 확인이 있는가. 기능이면 정상·예외 경로가 있는가
4. 인접 기능(리스트, 룰렛, 결과창, 이펙트)을 확인했는가
5. 공통 파일 변경 시 이슈에 사전 공유가 있는가
6. CI가 통과했는가
