# CI 파이프라인

본 문서는 음메 저장소에 코드를 통합하기 전에 수행하는 품질 검사의 범위와 절차를 정의한다. 배포 자동화(CD)는 다루지 않는다.

관련 문서: [코드 품질 유지](./02_maintaining_code_quality.md), [팀 약속](./00_team-agreement.md)

---

## 1. 품질 보증 (QA)

QA(Quality Assurance)는 제품이 기대한 품질을 유지하도록 하는 활동 전반을 의미한다. 실행 확인만이 아니라 이슈 작성, 재현 절차 공유, 코드 리뷰, 머지 전 확인을 포함한다.

| 구분 | 목적 | 예시 |
|---|---|---|
| 검증 (Verification) | 명세·이슈대로 동작하는지 확인한다 | 룰렛이 목록에 있는 메뉴만 선택하는지 |
| 확인 (Validation) | 실제 사용에 적합한지 확인한다 | 결과가 명확하고 재실행이 쉬운지 |

이슈는 종류별 템플릿을 사용하고, PR은 단일 템플릿을 사용한다. 리뷰는 요약, 변경 내용, 확인 방법, 테스트 계획을 기준으로 한다.

PR 리뷰 시 확인할 항목은 다음과 같다.

1. 변경 내용을 제3자가 재현할 수 있는가
2. 리스트, 룰렛, 결과창, 이펙트 등 인접 기능에 영향이 없는가
3. 빈 목록, 항목 1개, 새로고침 등 예외 상황을 검토했는가
4. 개인 환경의 로컬 경로나 비밀 키 없이도 실행할 수 있는가

## 2. 지속적 통합 (CI)

CI(Continuous Integration)는 기여자가 변경을 자주 `main`에 통합하고, 통합 전에 동일한 자동 검사를 수행하는 방식이다.

검사는 머지 이후가 아니라 **PR 생성 및 PR 브랜치 갱신 시점**에 실행한다. 기여자는 기능 브랜치에서 구현·확인한 뒤 해당 브랜치를 원격에 올리고 PR을 생성한다. `main`에 직접 푸시하여 검증하지 않는다.

### 기여자

- 작업 전 이슈를 등록한다 (`[버그]`, `[기능]`, `[질문]`)
- 변경을 작은 단위로 커밋하고, 단일 PR 템플릿에서 변경 종류를 표시한다
- 최신 `main`을 기능 브랜치에 반영하여 충돌을 장기간 방치하지 않는다
- 기능 브랜치에서 동작을 확인한 뒤 리뷰를 요청한다
- PR 테스트 계획의 린트·테스트 항목을 채운다

### 자동 검사

검사는 일반적으로 린트, 타입 검사, 테스트, 빌드 순으로 수행하며, 선행 단계가 실패하면 후속 단계를 생략할 수 있다.

| 단계 | 목적 | 실행 여부 | 예시 |
|---|---|---|---|
| 린트 | 스타일·단순 오류 패턴을 정적 분석한다 | 애플리케이션을 실행하지 않음 | 들여쓰기 오류, 미사용 변수, 포맷 불일치 |
| 타입 검사 | 값의 타입이 선언과 일치하는지 확인한다 | 애플리케이션을 실행하지 않음 | 시퀀스 인자에 문자열 전달, `None`에 속성 접근 |
| 테스트 | 정의한 입력에 대해 기대한 출력이 나오는지 확인한다 | 대상 코드만 실행 | 메뉴 3개일 때 선택 결과가 해당 목록에 포함됨 |
| 빌드 | 소스로부터 실행 산출물을 생성한다 | 조립 과정을 실행 | 번들 또는 설치 파일 생성 |

본 프로젝트는 Python 스크립트 중심으로, 현재 단계에서는 빌드가 필수이지 않다. 타입 검사는 타입 정보를 사용하는 경우에 도입한다.

각 단계의 한계는 다음과 같다.

- 린트는 동작 오류(예: 빈 목록에서의 예외)를 보장하지 않는다
- 타입 검사는 타입이 맞는 잘못된 로직을 걸러내지 않는다
- 테스트는 작성된 케이스만 검증한다. 사용성 판단은 리뷰에서 수행한다
- 빌드 성공은 동작 정확성을 의미하지 않는다

워크플로 파일만으로 머지가 차단되지는 않는다. `main`에 대한 브랜치 보호(Branch protection)를 설정해야 검사 실패 시 머지를 금지할 수 있다.

## 3. 파이프라인

파이프라인은 자동 검사의 실행 순서를 정의한 작업 열이다. 한 단계가 실패하면 이후 단계를 진행하지 않는다. 모든 PR에 동일한 규칙을 적용한다.

```
이슈 등록 → 기능 브랜치에서 구현
  → PR 생성 (템플릿 선택)
  → 저장소 체크아웃
  → 실행 환경 구성 (런타임·의존성 설치)
  → 린트
  → 테스트 (테스트가 있는 경우)
  → 타입 검사·빌드 (도입한 경우)
  → 성공 또는 실패 기록
  → 리뷰·머지
```

GitHub에서는 `.github/workflows/`의 워크플로 파일로 파이프라인을 정의하고, GitHub Actions가 이를 실행한다. Actions 실행 환경은 기여자의 로컬 환경과 분리되어 있으므로, 로컬 전용 파일이나 커밋되지 않은 비밀 값에 의존하는 변경은 검사와 재현에 실패한다.

저장소 규모가 커지면 변경 경로에 따라 검사를 분할할 수 있다. 현재 규모에서는 단일 작업(job)으로 구성한다.

## 4. 통합 절차

기능은 담당자가 구현하고, 품질 확인과 통합은 역할에 따라 분리한다. 작성자는 자신의 PR을 단독으로 승인하지 않는다.

| 단계 | 담당 | 내용 |
|---|---|---|
| 이슈 | 기능 담당 | `bug-report`, `feature-template`, `qua-report` 중 하나를 사용한다 |
| 구현 | 기능 담당 | 기능 브랜치에서 구현하고 동작을 확인한다 |
| PR | 기능 담당 | 단일 PR 템플릿에 종류, 관련 이슈, 테스트 계획을 채운다 |
| CI | GitHub Actions | 린트, 테스트 등 자동 검사를 수행한다 |
| 리뷰 | 리뷰·품질 담당 | 템플릿 항목과 인접 기능, 재현 가능성을 검토한다 |
| 머지 | 개발 리드 | 리뷰와 CI가 통과한 PR을 `main`에 병합한다 |

버그 PR은 `Fixes #`로 버그 이슈를, 기능 PR은 `Closes #`로 기능 이슈를 연결한다. 공통 모듈(`main.py` 등)을 변경할 때는 팀 약속에 따라 이슈 댓글로 먼저 알린다.

CI 통과는 자동 검사 기준을 만족했다는 의미이다. 화면 동작의 적절성과 템플릿에 적힌 수동 확인은 리뷰에서 판단한다. 리뷰 의견과 무관하게 자동 검사가 실패하면 해당 오류를 해소한 뒤 리뷰를 종결한다.

## 5. 적용 범위

본 프로젝트는 설치 패키지를 배포하지 않으므로 CD는 도입하지 않는다. CI는 다음을 최소 구성으로 한다.

1. `.github/workflows/ci.yml`에서 파이프라인을 정의한다
2. PR 생성 시 의존성 설치, 린트, 테스트(있는 경우)를 실행한다
3. PR에서 검사 결과와 템플릿의 테스트 계획을 확인한 뒤 리뷰를 진행한다
4. `main` 병합은 CI 통과와 리뷰 승인을 전제로 한다

타입 검사와 빌드는 기술 스택이 확정된 뒤 추가한다. 자동 검사가 반복 가능한 오류를 담당하면, 리뷰는 기능 정확성과 인접 기능 영향 확인에 집중한다.
